# 评论采集

## 需求

- 默认采集 **50 条**、字数 **≥15 字**、且**不含"第X季"或"更新"** 的剧评；
- 词条页提供 **"继续加载"** 按钮，点击后追加下一批评论（默认 30 条/批）并重新总结；
- 用户无需手动打开剧评页，点分享即可直接出词条。

## 数量语义（精确截断）

两个采集参数均为**精确上限**语义，发给 AI 的条数不会超出设置值：

- **首次采集评论数**（`target_count`）：首次采集完成后交给 AI 的合格评论**恰好 ≤ 该值**。
  由于评论按页拉取（每页 `page_count` 条原始评论，过滤后合格数不定），
  逐页累加时只补足剩余缺口（`page.comments.take(target - 已有数)`），
  不会出现"目标 10 条却发出 11 条"的超量问题。
- **单批加载条数**（`page_count`）："继续加载"时本批新增合格评论数同样**恰好 ≤ 该值**，
  补页循环受批次上限约束（`batchCount < batchCap`）。

实现位置：`Pipeline.startInitialCollect` / `Pipeline.loadMore` 中的 `take()` 截断。

> 历史问题记录：早期版本在拉取下一页前才检查目标数、整页照单全收，
> 导致"目标 10、实际 11"（如第一页合格 9 条 + 第二页合格 2 条）；
> 且字数过滤曾误写为 `> 10`，与规格 `> 20` 不符，后均已修正。

## 方案选型

**不自己实现网络请求。** 红果短剧的 RPC 框架（bytedance rpc）带有设备公共参数、
签名等逻辑，自行重放极易失效。因此选择**反射调用 app 内部接口**，
让 app 自己完成请求与签名：

```java
// com.dragon.read.saas.ugc.rpc.CommentApiService —— 类名未混淆，public static
public static Observable<GetCommentListResponse> getCommentListRxJava(
    GetCommentListRequest request)
```

app 剧评页（`uv1.m`）正是通过包装层 `h.e(request)` 调用同一底层方法；
直接调用 `getCommentListRxJava` 绕开了混淆类 `h`，依赖面更小。

## 请求构造（复刻剧评页 uv1.m 的参数）

| 字段 | 值 | 说明 |
|---|---|---|
| `groupID` | seriesId | 剧 id，即 URL 路径 `/novel/commentapi/comment/list/{group_id}/v1` 中的 group_id |
| `count` | 10（可配置 5~30） | 每页条数 |
| `cursor` | 上一页响应的 `common_list_info.cursor` | 首页为 null |
| `sort` | `UgcSortEnum.SmartHot` | 智能热评排序 |
| `groupType` | `UgcRelativeType.Book` | |
| `commentType` | `UgcCommentGroupTypeOutter.Book` | |
| `commentSource` | `UgcCommentSourceEnum.NovelBookComment` | |
| `serverChannel` | `UgcCommentChannelEnum.NovelPlayletCommentInnerList` | |
| `businessParam.bookID` | seriesId | |
| `businessParam.needCount` | false | 剧评页拉取下一页时即置 false |

以上枚举均通过 `Enum.valueOf` 反射构造（保留名）。
`appID` / `complianceStatus` 在 app 内由包装层填充，实测缺省可正常返回；
若后续版本校验，可再反射 `com.dragon.read.lib.community.inner.c` 补填。

## 响应解析

```
GetCommentListResponse
 └─ data: CommentListData
     ├─ dataList: List<UgcMixData>
     │    └─ reply: UgcReply
     │        └─ common: CommentCommon
     │            └─ content: CommentContent { text }   ← 评论文本
     └─ commonListInfo: { cursor, hasMore, total }      ← 分页游标
```

过滤规则（`shouldKeep`，正则用 `containsMatchIn` 即 `.*pattern.*` 语义）：

1. **字数下限**：`text.trim().length >= 15`（`MIN_TEXT_LENGTH = 15`）；
2. **排除型规则**（`EXCLUDE_PATTERNS`，命中任一即丢弃）：
   - `第.+季`——多为剧名/续季宣传语（如"等第3季"）；
   - `更新`——多为催更、版本更新讨论，对剧情判断无价值。

`reply` 为空时回退尝试 `comment` 字段（`UgcComment` 与 `UgcReply` 同构），
防御部分数据条目类型差异。

### 评分采集

每条评论的评分取自 `reply.expand.score`（`CommentExpand.score`，字符串数字，
如 `"8.5"`；未评分/解析失败为 null，计 0 分参与统计）。

### 状态栏统计（词条页）

词条页状态行固定格式：**"总x条评论,参考y条,平均得分z"**

- **x** = 总采集条数：全部抓到的评论（含被字数过滤丢弃的），按文本去重累计；
- **y** = 参考条数：累计交给过 AI 的合格评论数（含历史批次与恢复会话）；
- **z** = 平均得分 = 全部已采集评论评分总和 ÷ x（保留 1 位小数）。

统计随每页采集实时累计（`Pipeline.accumulateRaw`），并随日志库持久化
（`comment.score` 列 + `series` 聚合回读），杀 app 重开后仍正确。

阻塞式取回：调用 `Observable.blockingSingle()`，在 Pipeline 的工作线程中执行，
避免在主线程做网络等待。

## 分页编排（Pipeline.kt）

单线程池串行执行（防止并发打爆 RPC），状态机：

```
IDLE ──点分享──> COLLECTING（循环拉页，最多10轮，逐页补足至恰好 50 条 或 hasMore=false）
     ──> AI_PENDING ──> DONE
DONE ──"继续加载"──> COLLECTING（补1~3页）──> AI_PENDING（全量重新总结）──> DONE
任一步失败 ──> ERROR（词条页提供"重试"按钮）
```

采集进度实时回调到词条页状态栏（`正在采集剧评 30/50...`）。
若某页过滤后合格评论过少（<5 条），自动再补拉一页（最多补 2 次）。

## 模型类名依赖

依赖的全部类名均为**未混淆保留名**（含 `@SerializedName` 的 bean 与 RPC 服务类）：

- `com.dragon.read.saas.ugc.model.*`：`GetCommentListRequest`、`CommentBusinessParam`、
  `CommentListData`、`UgcMixData`、`UgcReply`、`CommentCommon`、`CommentContent`
- 枚举：`UgcSortEnum`、`UgcRelativeType`、`UgcCommentGroupTypeOutter`、
  `UgcCommentSourceEnum`、`UgcCommentChannelEnum`
- `com.dragon.read.saas.ugc.rpc.CommentApiService`

若 app 大版本改版导致模型字段变动，只需调整 `CommentFetcher` 中的字段名常量。
